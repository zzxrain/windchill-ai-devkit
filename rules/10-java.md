# Java 开发规则

本规则只定义 AI Agent 在企业 Java 项目中需要特别遵守的高价值工程约束。
更具体的 Windchill、项目或框架规则优先于本规则。

## 1. 保持 Java 版本兼容

必须以项目实际 JDK 和 Java Language Level 为准。

除非任务明确要求，不得：

- 使用目标 Java 版本不支持的语言特性或 API
- 修改 source / target / release 等编译版本
- 主动升级 JDK、框架或依赖版本

不得为了采用“更现代”的 Java 写法破坏现有平台兼容性。

## 2. 坚持最小必要修改

只修改完成当前任务所必需的代码。

不得顺带：

- 重构无关代码
- 大规模重命名或重新格式化
- 改变现有 package 或公共 API
- 替换已有框架或实现模式
- 创建没有明确价值的新抽象层

修改已有模块时，应优先保持该模块已经形成的代码和 API 风格。

## 3. 保持类型安全

新代码应尽量使用明确的泛型和类型，不得无必要引入 Raw Type、不安全类型转换或大范围 `@SuppressWarnings`。

如果平台或遗留 API 导致 unchecked 操作无法避免：

- 确认数据实际类型
- 将转换和 `@SuppressWarnings` 限制在最小作用域
- 不得使用 `@SuppressWarnings("all")` 掩盖问题

## 4. 谨慎处理共享状态与并发

服务器端代码不得假设只有单线程访问。

未经明确设计，不得主动引入：

- 可变 `static` 状态
- 自建全局 Cache
- 自建 Thread / Executor
- `parallelStream()`
- 粗粒度 `synchronized`

如果必须存在共享状态，应明确考虑线程安全、生命周期、内存释放、缓存失效及集群环境。

## 5. 正确管理资源生命周期

只有当前代码负责创建和拥有的资源才应由当前代码关闭。

对自己创建的 `AutoCloseable` 资源，应优先使用 try-with-resources。

不得关闭由 Windchill、应用服务器、框架或调用方管理生命周期的资源。

## 6. 不得擅自增加或替换依赖

实现功能时优先使用：

1. JDK 已有能力
2. 项目已有代码和依赖
3. 平台正式提供的 API

除非任务或项目设计明确要求，不得：

- 新增第三方运行时依赖
- 升级已有依赖
- 使用 JDK Internal API
- 使用 Reflection 绕过正常 API

## 7. 关注真正的性能风险

不得进行无依据的微优化。

优先检查：

- 循环中的数据库查询
- 循环中的远程调用
- 重复 IO
- 大结果集和大对象
- 明显的 N+1 调用
- 不必要的共享状态

性能优化不得以破坏代码正确性、平台语义或可维护性为代价。

## 8. 工具能够确定的事情交给工具

代码格式、import 顺序、缩进等确定性问题优先交给：

- IDE Formatter
- Compiler
- Checkstyle / Spotless
- PMD / Sonar
- 项目已有静态检查

AI 不得为了自己的代码风格偏好重新格式化无关代码。
